# OpenAPI and Swagger documentation

- **Requirement:** Maintain one validated OpenAPI 3.x contract for every HTTP API. Backend endpoint changes must document operation IDs, summaries, parameters, authentication, request bodies, success/error responses, status codes, examples, and reusable schemas in the same change. Annotations or generated specifications must match runtime validation and authorization behavior. Frontend API changes must inspect the published contract, preserve schema compatibility, and update generated clients, types, mocks, and contract tests where those mechanisms exist; do not add server-side Swagger annotations to Angular code.
- **Why:** The frontend and backend deploy independently, and stale Swagger documentation creates integration defects, unsafe assumptions, and unusable generated clients.
- **Enforcement:** Validate the OpenAPI document, fail on duplicate operation IDs or unresolved references, run backward-compatibility diff checks against the base branch, and exercise producer-consumer contract tests. Publish Swagger UI only with environment-appropriate access controls; never expose internal endpoints, secrets, credentials, or real personal data in examples.
- **Exceptions:** Internal health endpoints may omit rich examples when their schema and response codes remain documented. Temporary documentation gaps require an owner, tracked issue, expiry date, and explicit reviewer approval; breaking contract changes still require versioning and migration approval.
- **Evidence:** OpenAPI diff, validation and compatibility-check output, representative sanitized examples, backend tests proving documented responses, frontend type/client validation, affected consumer list, and rollout or rollback plan.
